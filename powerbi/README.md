# Power BI report

## Status — read this first

**The `.pbix` file and its screenshots are not in this directory, and I
could not produce them.** Power BI Desktop is Windows-only; this project
was built on macOS. `.pbix` is a proprietary container holding a compiled
Analysis Services model, and hand-writing a valid one is not something
that can be faked convincingly — a file that opened to errors would be
worse than an honest gap.

What *is* here is everything that does not require the application:

| File | What it is |
|---|---|
| `airindex_daily.csv` | The flat export. 226,200 rows, regenerated by `jobs/publish.py`. Gitignored — run publish to create it. |
| `model.pq` | Power Query (M) script: loads the CSV with explicit types and adds `month_name`, `season`, `is_usable`. |
| `measures.dax` | Every DAX measure the four pages need, with the reasoning in comments. |
| this file | Page-by-page build instructions. |

Opening Power BI Desktop and following §3 below reproduces the report in
roughly fifteen minutes. **To finish this phase properly, that has to be
done on a Windows machine, and the resulting `.pbix` plus screenshots
committed here.**

## 1. Generate the export

```bash
cd backend
.venv/bin/python -m jobs.publish
```

Writes `powerbi/airindex_daily.csv` — one row per station, date and
parameter, denormalised so the report needs no relationships to be useful
on first open. `band` and `completeness_flag` are precomputed by
`app/bands.py` so the report's colour logic cannot drift from the
application's.

## 2. Load it

Power BI Desktop → **Home ▸ Transform data ▸ Advanced Editor** → paste
`model.pq`, correcting the file path on the first line. Then
**Home ▸ Close & Apply**.

Name the table `airindex`. Paste the measures from `measures.dax`
(**Modeling ▸ New measure**, one at a time).

Two model settings that are not optional:

- Sort `month_name` by `month` (select the column ▸ **Column tools ▸ Sort
  by column ▸ month**). Otherwise every month axis orders alphabetically:
  Apr, Aug, Dec, Feb…
- Set `lat`/`lon` data category to **Latitude**/**Longitude**
  (**Column tools ▸ Data category**), or the map visual will try to
  geocode them as numbers.

## 3. The four pages

### Page 1 — Overview

- **Cards**: `Stations Total`, `Stations Reporting`, `Stations Silent`,
  `Mean PM2.5`, `Coverage %`.
- **Map** (bubble): `lat`/`lon`, size = `Mean PM2.5`, colour = `Band Of
  Mean` with the six CPCB colours below.
- **Line chart**: `reading_date` (month level) on the axis, `Mean PM2.5`
  on values — the national trend.
- **Slicers**: `year`, `state`, `parameter`.

Put a text box on this page carrying the provenance line from
`data/raw/provenance.json`. If the data is synthetic, the report must say
so on its face, the way the web application does.

### Page 2 — City league table

- **Table**: `city`, `state`, `Mean PM2.5`, `Max PM2.5`, `Band Of Mean`,
  `Stations Total`, `Coverage %`, `Share Over CPCB 60`.
- Conditional formatting on `Mean PM2.5` using the band colours as
  **rules**, not a continuous gradient — the bands are categorical
  thresholds and a gradient would imply a smoothness they do not have.
- Sort by `Mean PM2.5` descending.
- **Bar chart**: top 15 cities by `Mean PM2.5`.

### Page 3 — Seasonal profile

- **Clustered column**: `month_name` on the axis, `Mean PM2.5` on values,
  `city` on the legend (limit to 3–5 cities with a slicer).
- **Cards**: `Winter Mean`, `Monsoon Mean`, `Winter Multiple`.
- **Matrix**: rows `city`, columns `season`, values `Mean PM2.5`.

Add a text box pointing at `docs/methodology.md` §6. `Winter Multiple` is
the number a reader will want to explain, and the honest answer is that
this data cannot separate weather from seasonal emissions — the write-up
demonstrates the method reporting 63% weather-attribution on a dataset
where the true figure is 0%.

### Page 4 — Data quality

The page that makes the report trustworthy rather than decorative.

- **Cards**: `All Days`, `Usable Days`, `Coverage %`, `Mean
  Completeness`.
- **Column chart**: `station` on the axis, `Coverage %` on values, sorted
  ascending, with a reference line at 50%. Everything left of the line
  renders grey in the application and carries no band.
- **Matrix heatmap**: rows `station`, columns `year`-`month`, values
  `Coverage %` — this makes outages visible as blocks rather than as a
  dip in an average.
- **Table**: `station`, `city`, `Stations Silent`, min/max `reading_date`.
- **Slicer**: `completeness_flag`.

## 4. Band colours

|---|---|---|
| Good | 0–30 | `#157F73` |
| Satisfactory | 31–60 | `#4FA79A` |
| Moderate | 61–90 | `#E6C351` |
| Poor | 91–120 | `#E08A3C` |
| Very poor | 121–250 | `#C9497C` |

## 5. Two things the report must not do

**Do not average across `parameter`.** PM2.5 and PM10 are different
quantities on the same scale; a mean over both is meaningless. Every
concentration visual needs `parameter` filtered or on the legend.

**Do not let low-completeness days into a concentration average.** Every
measure in `measures.dax` that returns a concentration filters
`is_usable = TRUE`. If you add a measure, do the same. The coverage page
is the only place low-completeness rows should be counted, and there they
are the subject rather than the input.
