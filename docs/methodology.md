# Methodology

How AIRINDEX gets its numbers, the decisions that shaped them, and what
they cannot be used for. The companion document
[`data_quality_report.md`](data_quality_report.md) carries the row counts
and per-station completeness; it is regenerated by `jobs/clean.py` and is
a deliverable, not a debug artefact.

---

## 1. What the numbers are

Every value in this project is a **24-hour mean concentration**, in
µg/m³ (mg/m³ for CO). Not an AQI.

The National Air Quality Index most Indian readers are familiar with is a
piecewise-linear transform of exactly this quantity onto a 0–500 scale,
taking the worst sub-index across pollutants. Two reasons this project
reports the concentration instead:

1. The transform is lossy and not invertible in a useful way. An AQI of
   250 could be several different PM2.5 concentrations depending on which
   pollutant drove it.
2. A concentration can be checked against a standard. "91 µg/m³ of PM2.5"
   sits against the CPCB 24-hour limit of 60 and the WHO guideline of 15.
   "AQI 250" sits against nothing a reader can independently verify.

The six colour bands are the CPCB NAQI **category breakpoints**, stated as
concentration ranges. For PM2.5: Good ≤30, Satisfactory ≤60, Moderate ≤90,
Poor ≤120, Very poor ≤250, Severe above. The table lives in
`backend/app/bands.py` and is duplicated in `frontend/src/lib/bands.js`
(the frontend must work with the API stopped); `tests/test_bands.py`
parses the JavaScript and asserts the two agree, so they cannot drift.

## 2. How the data moves

```
OpenAQ v3  ──collect.py──▶  data/raw/       hourly parquet, by year
                                │
                            clean.py        6 rules, every drop counted
                                ▼
                            data/clean/     daily parquet, by month
                                │           + docs/data_quality_report.md
                            load.py
                                ▼
                            MariaDB         stations, readings_daily
                                │
                          publish.py
                                ├──▶ frontend/public/snapshot.json
                                └──▶ powerbi/airindex_daily.csv
```

**The collector pulls hourly, not daily.** OpenAQ will serve daily means
directly, and using them would have been less work. Two of the cleaning
rules make it impossible: a flatline is defined over *consecutive hours*,
and `n_hours`/`completeness` cannot be recovered from an average somebody
else has already taken. Accepting a precomputed daily mean means accepting
whatever hours went into it, unseen.

**The parquet lake is kept as well as the database.** The API serves the
application from MariaDB; the Phase 6 analysis reads the parquet directly
with DuckDB. Neither has to accommodate the other.

## 3. Spatial on MariaDB 10.4 — and the axis-order trap

This is the part of the build most likely to be silently wrong, so it is
documented at length.

### The environment

XAMPP ships **MariaDB 10.4**. The original schema for this project was
written in MySQL 8 dialect and does not run on it. Three incompatibilities,
each verified against 10.4.28:

| Intended (MySQL 8) | On MariaDB 10.4 | Resolution |
|---|---|---|
| `geom POINT SRID 4326` | `SRID` column attribute is a syntax error | plain `POINT NOT NULL` |
| `ST_SRID(POINT(...), 4326)` | 10.4's `ST_SRID` is a one-argument *getter* | dropped; no SRID needed |
| `geom` as a `GENERATED … STORED` column with `SPATIAL INDEX` | generated columns cannot be `NOT NULL`; `SPATIAL INDEX` requires every part to be `NOT NULL` | `BEFORE INSERT`/`BEFORE UPDATE` triggers |

`ST_Distance_Sphere` **is** available in 10.4, contrary to a common
assumption that it arrived in 10.7. It was tested, not assumed.

### The axis order

The received wisdom is that *MySQL uses latitude-first axis order for
SRID 4326*. That is true — **of MySQL 8 with an SRID-aware geometry**,
because SRID 4326 follows the EPSG axis definition, which is (lat, lon).

MariaDB 10.4 has no SRID-aware geometry at all. Its `POINT` is plain
cartesian `(x, y)`, and `ST_Distance_Sphere` reads **x as longitude**.
The correct construction here is `POINT(lon, lat)` — **longitude first**,
the opposite of the advice.

Measured, not reasoned:

| Construction | Delhi → Mumbai | Correct? |
|---|---|---|
| `POINT(lon, lat)` | 1157.20 km | ✅ matches haversine to 5 decimal places |
| `POINT(lat, lon)` | 560.30 km | ❌ wrong by a factor of two |

The failure mode is what makes this dangerous: the wrong order still
returns a plausible number. Nothing errors. A nearest-station query would
just quietly return the wrong station.

**Containment.** The two triggers at the bottom of `backend/schema.sql`
are the only code in the project that constructs a geometry. Everything
else reads `geom`. `backend/tests/test_axis_order.py` asserts the distance
against an independent haversine implementation to within 1% across five
city pairs, *and* asserts that latitude-first is still wrong — so a move
to MySQL 8, where the answer flips, fails loudly instead of passing by
accident.

An independent cross-check fell out of the frontend work: the browser's
offline nearest-station fallback computes haversine in JavaScript, with no
geometry type involved. For Connaught Place it returns ITO at **3.52 km**;
MariaDB returns **3.52 km**. Two implementations, no shared code.

### Why the bounding box

`sql/nearest.sql` filters on a lat/lon box before computing distance.
Distance functions are not sargable, so ordering by `ST_Distance_Sphere`
alone scans the table; the box turns it into a B-tree range scan on
`ix_lat_lon`.

The box half-widths are computed from `max_km` in Python rather than
hardcoded, because a degree of longitude is ~111 km at the equator and
~96 km at Srinagar. A fixed 0.5° would clip real candidates in the north
and over-scan in the south. See `routes/stations.py:_bounding_box`.

## 4. Cleaning

Six rules, applied in order, every drop counted and attributed to exactly
one rule so the totals reconcile. Full counts in
[`data_quality_report.md`](data_quality_report.md).

| # | Test | Action |
|---|---|---|
| 1 | `value < 0` | drop |
| 2 | `value == 0`, PM2.5/PM10 only | drop |
| 3 | `value ∈ {999, 9999, −999}` | drop |
| 4 | PM2.5 > 1000, PM10 > 2000 | drop |
| 5 | identical value ≥ 6 consecutive hours | drop the run |
| 6 | day built from < 6 hours | **keep, flag** |

Notes on the ones with judgement in them:

- **Rule 2 is restricted to particulates.** A gas can legitimately read
  zero. An exact zero for PM is an instrument reporting nothing.
- **Rule 3 has to be explicit.** 999 µg/m³ of PM2.5 is not physically
  impossible, so rule 4 would not catch it. It is a legacy no-data
  sentinel that arrives looking like a measurement.
- **Rule 5 is the most important one.** A stuck sensor is more dangerous
  than a missing one, because it has a plausible magnitude *and* it fills
  the gap that would otherwise be visible. Runs are counted in rows, not
  clock hours: a gap in the middle of a stuck spell does not unstick the
  instrument, and treating the two halves separately would let a 20-hour
  flatline through as two 5-hour ones.
- **Rule 6 does not drop.** A sparse day is still information; it just
  cannot carry a colour.
- **Ordering matters for attribution.** An hour reading −999 is counted
  as negative (rule 1), not as a sentinel (rule 3). First match wins, so
  the counts sum to the total instead of double-counting overlaps.

## 5. Completeness, and the one thing this project refuses to do

`completeness = n_hours / 24 × 100`. The denominator is the **day**, not
the hours the instrument happened to report. Dividing by hours observed
would make every day 100% complete by construction and the column would
say nothing.

**A station that is not reporting must never look like clean air.** This
is the single most important correctness property in the application, and
it is not automatic — a station that stopped transmitting six weeks ago
still has a "latest" value, and that value was measured on a day that was
itself complete. A naive implementation colours it green.

So a band is withheld unless **both** hold:

- the latest day is ≥ 50% complete, and
- the **30-day window** is ≥ 50% complete.

The second test is what catches the silent station. Where a band is
withheld the API returns `band_withheld` — a sentence saying which test
failed — and the interface shows it verbatim rather than leaving an
unexplained grey dot. Grey markers are additionally **hatched**, so the
distinction survives greyscale printing and colour blindness.

30-day completeness is `SUM(n_hours) / (30 × 24)`, not the average of the
daily completeness values. A station that reported three perfect days and
then went silent scores ~100% by the averaging definition and ~10% by
this one. The second is the truth.

City-level completeness divides by `stations × days × 24`. An earlier
version divided by distinct dates only, which made the figure scale with
station count — Delhi's seven stations reported 659% complete. That was
caught in the browser, and it mattered beyond the wrong label: the same
figure gates whether a city gets a band at all.

## 6. Analysis: does weather explain Delhi's winter?

Full output: [`../analysis/output/winter_rise_delhi.md`](../analysis/output/winter_rise_delhi.md).
Reproduce with `analysis/fetch_weather.py` then `analysis/winter_rise.py`.

**Question.** Delhi's PM2.5 roughly doubles in winter. Winter is also
colder, calmer and drier. How much of the rise is weather trapping the
same emissions, and how much is more being emitted?

**Design.** Regress `log(PM2.5)` on a winter indicator (Nov–Jan), first
alone and then adding ERA5 meteorology: log wind speed, gust maximum,
mean temperature, diurnal range, a rain-day indicator, shortwave
radiation, and wind direction as sin/cos components. Unit is the city-day.
Standard errors are Newey–West with 30 lags, because daily air quality is
strongly autocorrelated and classical errors would be far too small.

**Result on this dataset.** The winter coefficient falls from +0.785
(×2.19 in levels) to +0.289 (×1.33) when weather is added — nominally
63% "explained by weather".

**Why that number should not be believed.** Regressing the winter
indicator *on the weather controls alone* gives an R² of **0.62**. About
62% of "winter" is reconstructible from temperature, radiation and wind.
In Delhi, winter and winter weather are very nearly the same variable.
Adding the controls therefore removes part of the calendar along with
part of the meteorology, and the winter coefficient would fall even if
weather did nothing at all.

**A demonstration, courtesy of the synthetic fixture.** The PM2.5 in the
default dataset is generated by `jobs/synth.py`, whose winter peak comes
from a *calendar* multiplier and whose day-to-day variation comes from an
autocorrelated random walk. Neither reads the weather. **The true weather
contribution in this dataset is exactly zero.** The method reports 63%.

That 63-point gap is not a coding error — the regression is correctly
specified and correctly fitted. It is a measurement of the *design's*
bias, obtainable only because the data-generating process is known. On
real data it would not be, which is precisely the reason to distrust the
headline figure. **Read any such share as an upper bound on weather's
contribution, never as an estimate of it.**

A credible causal answer needs variation in weather that is independent
of the season: comparing unusually windy Januaries with unusually still
ones *within* month, rather than comparing January with July.

### Confounders I could not rule out

1. **Weather and emissions are not independent.** Cold causes both poor
   dispersion and more combustion for heating. Controlling for temperature
   absorbs some genuine emissions response. Biases the weather share
   **up**.
2. **Crop-residue burning is seasonal and unmeasured.** Stubble burning in
   Punjab and Haryana coincides with the onset of the inversion. Wind
   direction is a crude proxy — it says air came from the north-west, not
   whether anything was burning there.
3. **ERA5 is a model, not a measurement at the monitor.** ~25 km
   reanalysis grid. Street-level wind at a roadside monitor differs, and
   the error is not random with respect to urban form: dense built-up
   areas are systematically calmer than the grid cell implies.
4. **Boundary-layer height is missing.** The most physically direct
   control for accumulation. The Open-Meteo archive returns nulls for it
   at this location; `diurnal_range` and `temperature_2m_min` stand in as
   weaker inversion proxies. This biases the weather share **down** —
   opposite to confounder 1. I cannot say which dominates.
5. **Diwali moves** between mid-October and mid-November, so a fixed month
   dummy smears a large one-to-three-day emissions spike across the
   winter boundary differently each year.
6. **The station network is not fixed.** A monitor commissioned in a
   cleaner suburb lowers the city mean with no change in anyone's air.
7. **Regional transport is not local weather.** Delhi sits downwind of a
   large emitting region. Local wind speed describes ventilation, not what
   arrives.
8. **This is association, not causation.** No instrument, no
   discontinuity, no randomisation.

## 7. What this dataset cannot show

- **A gap is not clean air.** Covered in §5. It is the property the whole
  completeness apparatus exists to protect.
- **Station siting is not recorded.** A roadside monitor and a background
  monitor a kilometre apart measure genuinely different air; nothing here
  distinguishes them, and city averages mix the two.
- **A city average is a mean of monitors** — not of people, and not of
  area. The "national" figure leans towards wherever the network is
  dense, which is the polluted north.
- **State is a lookup, not source data.** OpenAQ v3 provides a country and
  a `locality`, never a state. `jobs/regions.py` fills it from a
  city→state table and returns `None` for anything not in it.
- **Daily means hide the peaks.** A day averaging Moderate can contain
  Severe hours. Hourly data exists upstream; the daily figure is reported
  because that is what the standards are written against.
- **Concentration is not exposure.** Ambient outdoor concentration at a
  fixed monitor is not what any individual breathes. Indoor air,
  commuting and cooking fuel all matter and none are here.
- **Revisions happen.** OpenAQ backfills and corrects. A collection run
  next month may legitimately return different numbers for the same dates.
  `data/raw/provenance.json` records what produced any given lake.

## 8. Reproducing

```bash
# schema
/Applications/XAMPP/xamppfiles/bin/mysql -u root < backend/schema.sql

cd backend
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
cp .env.example .env        # set OPENAQ_API_KEY for real data

# real data
.venv/bin/python -m jobs.collect --all --years 5
# or, with no key, a deterministic fixture
.venv/bin/python -m jobs.collect --synthetic --to 2026-08-31 --years 5

.venv/bin/python -m jobs.clean
.venv/bin/python -m jobs.load --truncate
.venv/bin/python -m jobs.publish
.venv/bin/python -m pytest -q

# analysis
cd .. && ./backend/.venv/bin/python analysis/fetch_weather.py --city Delhi
./backend/.venv/bin/python analysis/winter_rise.py --city Delhi
```

The synthetic path is seeded and reproduces exactly. The API path will
not, and should not be expected to.

### A note on ports

The API defaults to **5001**, not 5000. On macOS, Control Center's AirPlay
Receiver listens on 5000 and answers with HTTP 403 — worse than a closed
port, because the application receives a reply from an unrelated service
instead of a clean connection failure, and "the API is down" presents as a
mysterious permissions error. `frontend/src/lib/api.js` additionally
treats any non-JSON response as offline, so the fallback engages rather
than surfacing a parse error.

## 9. Asia expansion

The collector has no India-specific logic. Country is one value:

```bash
.venv/bin/python -m jobs.collect --country TH --all --years 5
.venv/bin/python -m jobs.collect --verify-country-agnostic   # audit it
```

The one country-specific component is the optional city→state lookup in
`jobs/regions.py`, which returns `None` for an unknown country — leaving
`stations.state` NULL. A missing label, not a broken collector.
